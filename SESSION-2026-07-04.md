## Feature 1: Remote Reboot Command ✅ COMPLETE

### Purpose
Allow users to remotely reboot stations from the web dashboard, primarily to detect newly connected I2C sensors without physical access.

### Implementation Details

**Protocol Changes:**
- Added `MessageType::REBOOT = 0x0E` to protocol
- Payload: `[delay_seconds (uint8), flags (uint8)]`
- 5-second default delay allows ACK transmission before reboot

**Files Modified:**
```
lib/LoRaPNP/src/Types.h           - Added REBOOT message type
lib/LoRaPNP/src/Packet.cpp        - Added typeStr() case
node/src/main.cpp                 - handleRebootCommand() (37 lines)
src/main.cpp                      - handleReboot() API + UI (65 lines)
PROTOCOL-SPEC.md                  - Section 12.4 documentation
```

**Station Handler:**
- Validates payload and destination
- Sends ACK before rebooting (best effort)
- Logs reboot reason to NVS (0xFF = remote reboot)
- Delays specified seconds
- Calls `ESP.restart()`

**Gateway API:**
- POST `/api/reboot` with `{node_id: N}`
- Validates station exists in registry
- Sends REBOOT packet via LoRa
- Returns success/error to dashboard

**Dashboard UI:**
- Red "🔄 Reboot Station" button on each station card
- Confirmation dialog explains purpose
- Success message after sending command
- Full-width button with hover effects

**User Experience:**
```
1. User plugs in new sensor while station powered off
2. User powers on station
   OR: User clicks "🔄 Reboot Station" button remotely
3. Station reboots and re-detects all I2C sensors
4. Gateway dashboard updates automatically
```

**Safety Features:**
- Confirmation dialog prevents accidental reboots
- 5-second delay allows ACK transmission
- NVS logging for debugging
- Only processes when station is JOINED
- Gateway doesn't retry (station may have rebooted)

## Feature 2: I2C Sensor Detection Framework 🔨 IN PROGRESS

### Purpose
Automatically detect and register I2C sensors connected to stations without manual configuration.

### Architecture

**Sensor Registry Pattern:**
```
Sensor Driver Registry (table of known sensors)
    ├── SHT40Driver (0x44, 0x45)
    ├── BMP581Driver (0x46, 0x47)
    ├── SoilMoistureDriver (0x28)
    └── XM125Driver (0x52)

On station boot:
1. Scan I2C bus (0x03-0x77)
2. For each responding address:
   - Match against driver registry
   - Call driver's detect() function
   - If verified, call addSensors()
3. Send SENSOR_DESCRIPTOR packets to gateway
```

**Directory Structure:**
```
node/src/sensors/
├── SensorRegistry.h              - Registry interface
├── SensorRegistry.cpp            - Detection loop
└── drivers/
    ├── SHT40Driver.h/cpp         ✅ Complete
    ├── BMP581Driver.h/cpp        ✅ Complete
    ├── SoilMoistureDriver.h/cpp  📋 Stubbed
    └── XM125Driver.h/cpp         📋 Stubbed
```

### Protocol Extensions

**Added Sensor Types:**
```cpp
SENSOR_TYPE_SOIL_MOISTURE = 0x06
SENSOR_TYPE_DISTANCE = 0x07
SENSOR_TYPE_PRESENCE = 0x08
SENSOR_TYPE_LIGHT = 0x09
```

**Added Sensor Units:**
```cpp
SENSOR_UNIT_MILLIMETERS = 0x06
SENSOR_UNIT_BOOLEAN = 0x07
SENSOR_UNIT_LUX = 0x08
```

### Driver Interface

Each sensor driver implements:
```cpp
bool detect(TwoWire* wire, uint8_t addr)
    - Returns true if sensor verified at address
    - Should read chip ID register or verify response

uint8_t addSensors(I2CSensor* sensors, uint8_t max, uint8_t addr, uint8_t* next_id)
    - Creates sensor descriptor(s)
    - Returns number of sensors added
    - Example: SHT40 adds 2 (temp + humidity)
```

## Design Decisions

**Why Remote Reboot vs. Hot-Plug Detection?**
- Simpler implementation (one command vs. periodic scanning)
- More reliable (full reboot guarantees clean state)
- Lower power consumption (no background scanning)
- User controls when detection happens
- Documentation can specify "power cycle or reboot to detect sensors"

**Why Sensor Registry Pattern?**
- Extensible: New sensors = drop in new driver file
- Maintainable: Each sensor isolated in own driver
- Memory efficient: Function pointers in flash, minimal RAM
- Testable: Each driver can be tested independently
- Follows existing Adafruit/SparkFun library patterns

**Why Not Dynamic Library Loading?**
- ESP32 doesn't support runtime library loading
- Compile-time linking is more reliable
- All dependencies known at build time
- Simpler build system
